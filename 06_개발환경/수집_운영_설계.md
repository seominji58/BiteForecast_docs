# 공공데이터 자동 수집 운영 설계안 (검토용, 2026-11-09)

> 상태: **설계안 — 아직 적용하지 않음.** 검토·결정 후 진행한다. 이 문서의 4장 「이미 반영한 것」만 코드에 들어가 있다.

## 1. 현재 상태 (확인 결과)

| 항목 | 현재 | 문제 |
|---|---|---|
| 배포 환경 | **없음.** 백엔드는 개발 맥에서만 실행 (Docker·Fly·Render·GitHub Actions 등 배포 설정 파일 없음) | 운영 서버를 먼저 정해야 수집 방식을 정할 수 있음 |
| 수집 실행 | 터미널에서 `python -m app.jobs.collect --loop` (1시간마다) | 터미널을 닫거나 맥을 재시작하면 멈춤. 실제로 **11/5~11/9 수집 중단** |
| 실패 처리 | API 호출 단위 재시도(2회, 429 간격 조절)만 있음. 그 밖의 예외(DB 오류 등)가 나면 `--loop` 자체가 종료됨 | 한 번 죽으면 아무도 모름 |
| 실행 기록 | 터미널 로그뿐. DB 에 실행·실패 기록 없음 | 마지막 성공 시각·실패 원인을 화면이나 관리자가 알 수 없음 |
| 데이터 DB | SQLite 파일 1개 (`backend/biteforecast.db`) | 서버와 수집기가 같은 디스크를 써야 함 |

## 2. 요구사항
1. 서버·컴퓨터가 재시작돼도 정해진 주기(1시간)에 자동 수집
2. 실패 시 재시도, 연속 실패는 알림
3. 자료별 마지막 성공 시각 관리, 오래된 자료는 앱에서 최신처럼 보이지 않게
4. 같은 수집이 동시에 두 번 돌지 않게 (중복 호출로 인증키 호출량 초과 방지)
5. 로그에 인증키가 남지 않게

## 3. 설계

### 3-1. 실행 방식 — 배포 형태에 따라 선택 (결정 필요)

| 안 | 구성 | 장점 | 단점 | 추천 상황 |
|---|---|---|---|---|
| **A. 서버 1대(VM) + systemd timer** | 클라우드 VM 1대에 API 서버(systemd service)와 수집기(systemd timer, 매시 정각+5분) | SQLite 그대로 사용 가능, 재부팅 후 자동 시작, 비용 낮음 | VM 직접 관리(보안 업데이트) | **초기 출시 추천** — 지금 구조(SQLite·파일 사진 저장)를 거의 그대로 옮길 수 있음 |
| B. 관리형 플랫폼(Render·Fly 등) + 예약 작업 | 웹 서비스 + Cron Job(별도 컨테이너) | 서버 관리 부담 적음 | 서버와 수집기가 다른 컨테이너 → SQLite·사진 파일 공유 불가 → **PostgreSQL·객체 저장소로 전환 필요** | 사용자 증가 후 |
| C. API 서버 프로세스 안에서 예약(APScheduler) | 서버가 켜지면 스케줄러도 같이 시작 | 구성 단순 | 서버를 여러 대 띄우면 중복 실행, 서버 장애 = 수집 중단 | 비추천 |
| (개발용) 맥 launchd | `~/Library/LaunchAgents` 에 등록 | 개발 맥 재부팅 후에도 자동 수집 | 운영용 아님 | 지금 개발 중 데이터 끊김 방지용 |

### 3-2. 실행 기록과 마지막 성공 시각 (DB 추가 — 결정 후 구현)
- `collect_run`: 실행마다 1행 — 시작·종료 시각, 상태(성공/일부 실패/실패), 자료별 건수·오류 수, 오류 요약(인증키 제외)
- `dataset_status`: 자료별 1행 — 마지막 시도·**마지막 성공 시각**, 연속 실패 횟수, 마지막 오류
  - 자료: 조석 예보, 조위, 부이 실측, 기상청 단기예보, 해상 특보, 바다낚시지수
- 관리자 화면(`/api/v1/admin`)에 「수집 상태」 표시

### 3-3. 실패·재시도 규칙
| 단계 | 규칙 |
|---|---|
| API 호출 | 지금처럼 2회 재시도 + 429(호출 과다)면 간격 늘림 |
| 자료 단위 | 한 자료가 실패해도 다른 자료는 계속 수집 (지금도 동일) |
| 실행 단위 | 전체 실패 또는 예외 → **10분 뒤 1회 재실행**, 그다음은 정규 주기 |
| 예외로 종료 | 실행 1회가 예외로 끝나도 다음 주기는 그대로 돈다 (timer/cron 이 매번 새로 실행) |
| 알림 | 같은 자료 **3회 연속 실패** 또는 예보·특보 **3시간 넘게 성공 없음** → 관리자 알림 (방법 결정 필요: 이메일·슬랙 등) |

### 3-4. 중복 실행 방지
- 수집 시작 시 DB 잠금 행(`collect_lock`, 만료 시각 포함)을 잡고, 이미 잡혀 있으면 이번 실행은 건너뜀. 만료(예: 50분)되면 자동 해제 (비정상 종료 대비)

### 3-5. 로그와 인증키
- `httpx`/`httpcore` 요청 로그 끔 (**적용함**, 2026-11-09) — 요청 URL 에 `serviceKey` 가 들어가기 때문
- 오류 메시지를 기록할 때 인증키 문자열을 `***` 로 바꾸는 필터 추가 (구현 예정)
- 운영 로그는 서버 로그 수집 도구로 보내되 보관 기간 30일

## 4. 이미 반영한 것 (운영 환경 변경 없음)
- **자료 신선도 조회:** `GET /api/v1/meta/data-status` — 자료별 마지막 수집 시각, 예보·특보가 3시간 넘게 갱신되지 않으면 `stale`
- **앱 표시:** 홈 출조 탐색·조건으로 찾기·비교 기준 카드에 「기상청 예보·특보 ○○ 갱신 (n분 전)」. 오래됐으면 맞는 곳 개수·목록을 보여주지 않고 마지막 갱신 시각과 상태만 안내
- 특보는 원래도 3시간 넘으면 「확인 불가」(없음으로 단정하지 않음)

## 5. 결정 요청
1. 운영 서버 형태: **A(VM 1대, 추천)** / B(관리형 + DB 전환) / 기타
2. 클라우드 업체·지역 (예: 국내 리전 — 공공데이터 API 응답 속도·개인정보 보관 위치 고려)
3. 실패 알림 받을 방법 (이메일·슬랙·카카오 알림톡 등)
4. 개발 중 데이터 끊김 방지를 위해 개발 맥에 launchd 등록할지
