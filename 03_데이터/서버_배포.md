# 서버 배포 (Fly.io)

> 구성: 앱(iOS) → **Fly.io 백엔드(도쿄)** → **Supabase DB(서울)**. 수집은 GitHub Actions(매시 17분) → Supabase.
> Supabase 는 Python 서버를 돌릴 수 없어(Edge Functions = Deno 전용) 서버만 Fly.io 에 둠.

## 설정
| 항목 | 값 |
|---|---|
| 앱 | `biteforecast-api` → https://biteforecast-api.fly.dev/api/v1 |
| 지역 | nrt(도쿄) — Fly 에 서울 리전 없음, Supabase(서울)와 가장 가까움 |
| 서버 | shared-cpu-1x 256MB 1대, 요청 없으면 자동 정지·요청 오면 자동 시작 |
| 사진 | 볼륨 `media` 1GB → `/data/media` (기존 사진 5장 옮김, DB 경로 5/5 일치) |
| 비밀값 | `DATABASE_URL` 만 (fly secrets). 관리자 토큰 없음 → 관리자 기능 꺼짐 |
| 환경 | `APP_ENV=prod` (CORS 미들웨어 끔 — 모바일 앱은 영향 없음) |
| 파일 | `backend/Dockerfile`, `.dockerignore`(.env·DB·사진·백업 제외), `fly.toml` |
| 예상 비용 | 상시 켜도 서버 약 $2 + 볼륨 약 $0.15 / 월, 자동 정지로 더 적음 |

## 확인
- 상태 확인 `/api/v1/health` passing, `{"status":"ok","env":"prod"}`
- 응답 시간(도쿄→서울 DB): 홈 요약 첫 요청 2.9초·캐시 0.6초, 목록 1.5초, 상세 0.75초, 게시글 0.5초. 멈춰 있다 깨어날 땐 첫 요청 몇 초 더
- 서버 메모리 약 133MB / 256MB
- 앱: `frontend/.env` `EXPO_PUBLIC_API_URL` 을 Fly 주소로, Metro 재시작 → 홈 정상, Fly 로그에 앱 요청(`/me/account`·`/places-summary` 등 200) 확인

## 운영
- 배포: `cd backend && fly deploy --remote-only --ha=false`
- 로그: `fly logs --app biteforecast-api` / 상태: `fly status`
- 표 구조가 바뀌면 배포 **전에** Supabase 에 `alembic upgrade head` (서버는 버전이 다르면 시작 안 함)
- 로컬 개발로 돌아가기: `frontend/.env` 의 API 주소를 `http://127.0.0.1:8001/api/v1` 로 → Metro 재시작
- 되돌리기(삭제): `fly apps destroy biteforecast-api` — Supabase 데이터 영향 없음. **볼륨의 사진도 같이 지워지므로 먼저 받아 둘 것** (`fly ssh sftp`)

## 남은 점
- 사진 볼륨은 서버 1대에만 붙음 → 서버를 늘리려면 사진을 Supabase Storage 로 옮겨야 함
- 256MB 에서 큰 사진 여러 장을 동시에 처리하면 메모리 부족 가능 → 그때 512MB(약 $3/월)로
- 로컬 8001 서버도 같은 Supabase 를 씀 (개발용)
